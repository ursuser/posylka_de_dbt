# YESPO → BigQuery Integration: Design Spec

**Date:** 2026-04-02  
**Project:** Posylka DE (`posylka-de-478903`)  
**Status:** BLOCKED — pending YESPO support response (see API Exploration Results)

---

## Overview

Daily automated data loader: pulls data from YESPO (eSputnik) REST API and writes it to BigQuery dataset `posylka-de-478903.yespo_data`. Runs on GCP (Cloud Functions 2nd gen + Cloud Scheduler) before the daily Dagster/dbt pipeline.

---

## Architecture

```
Cloud Scheduler (04:00 UTC daily)
        │
        ▼
Cloud Function 2nd gen (Python 3.11)
        │
        ├── YESPO API ──► campaigns stats
        ├── YESPO API ──► contacts
        ├── YESPO API ──► activities (events per contact)
        └── YESPO API ──► orders
        │
        ▼
BigQuery: posylka-de-478903.yespo_data
        ├── campaigns
        ├── contacts
        ├── activities
        ├── orders
        └── _load_state   (backfill progress tracker)
        │
        ▼
Dagster runs dbt at 05:00 UTC → Power BI refreshes at 08:00 Berlin
```

---

## BigQuery Tables

All tables are date-partitioned. Writes use `WRITE_TRUNCATE` per partition (no duplicates).

| Table | Key fields | Partition by |
|---|---|---|
| `campaigns` | id, name, sent, opens, clicks, unsubscribes | send_date |
| `contacts` | id, email, phone, status, created_at, custom fields | — (full refresh daily) |
| `activities` | contact_id, message_id, campaign_id, event_type, timestamp | event_date |
| `orders` | order_id, contact_id, amount, status, items | order_date |
| `_load_state` | entity, last_loaded_date | — |

## Code Structure

Location: `dbt_project/yespo_project/` (sibling to `dagster_project/` and `pbi_project/`)

```
yespo_project/
├── main.py              # Cloud Function entry point
├── yespo_client.py      # HTTP client: auth, pagination, retry
├── loaders/
│   ├── campaigns.py
│   ├── contacts.py
│   ├── activities.py
│   └── orders.py
├── bq_writer.py         # BigQuery write logic (WRITE_TRUNCATE per partition)
├── state.py             # load mode detection: backfill vs incremental
├── requirements.txt
└── .env.example
```

### main.py flow

1. Read API key from Secret Manager (`yespo-api-key`)
2. Determine mode via `state.py`:
   - **backfill**: if `_load_state` table is empty or missing
   - **incremental**: load `today - 2` to `today`
3. Run all 4 loaders sequentially
4. Update `_load_state` on success
5. Log results to Cloud Logging

---

## Incremental Strategy

- **Daily incremental:** loads data for a 2-day window ending today (overlap guards against API delays)
- **Backfill (first run):** iterates in 30-day chunks from a configurable `BACKFILL_START_DATE` (default: `2026-01-01`) up to today
- **Resumability:** `_load_state` table tracks `last_loaded_date` per entity — if the function is interrupted mid-backfill, the next run resumes from the last checkpoint

---

## Reliability

- **API retry:** 3 attempts with exponential backoff on HTTP 429 and 5xx responses
- **Partial failure:** if one loader fails, remaining loaders continue; error is logged and function returns HTTP 500
- **HTTP 500 triggers Cloud Scheduler alert** to configured email

## Deployment

```bash
gcloud functions deploy yespo-to-bq \
  --gen2 \
  --runtime python311 \
  --region europe-west3 \
  --trigger-http \
  --no-allow-unauthenticated \
  --set-secrets YESPO_API_KEY=yespo-api-key:latest \
  --timeout 3600 \
  --memory 512Mi \
  --service-account posylka-de-478903-a9eebcf5fae4@posylka-de-478903.iam.gserviceaccount.com
```

Cloud Scheduler job: HTTP POST to function URL with OIDC token, cron `0 4 * * *`.

## API Exploration Results (2026-04-02)

Conducted live API exploration with actual API key. Base URL: `https://esputnik.com/api`, auth: HTTP Basic (any login + API key as password).

### What works

| Endpoint | Status | Notes |
|---|---|---|
| `GET /v1/account/info` | ✓ 200 | Returns orgId, organisationName |
| `GET /v1/contacts?startindex=1&maxrows=N` | ✓ 200 | Returns id, email (channel), languageCode, firstName, lastName |
| `GET /v1/addressbooks` | ✓ 200 | Returns address book with custom field definitions (DATE_OF_BIRTH, GENDER) |

### What requires YESPO support activation

| Endpoint | Status | Notes |
|---|---|---|
| `GET /v2/contacts/activity?dateFrom=...&dateTo=...` | ✗ 400 | Returns: "Contact support to enable ContactActivity" — paid feature, must be requested |

### What is unavailable via REST API

| Entity | Status | Notes |
|---|---|---|
| Campaign stats | ✗ 404 | No GET endpoint found (`/v1/campaigns`, `/v1/emails`, `/v1/mailings` — all 404) |
| Orders (read) | ✗ 405 | `GET /v1/orders` → Method Not Allowed. Orders are write-only (POST from shop to YESPO). Orders already exist in CRM (`stg_crm__orders.sql`). |

### Action required before implementation

2. **Ask YESPO** if there is a REST API endpoint for campaign-level statistics (total sent/opens/clicks per campaign). If not — ask about CSV export or alternative data access.
3. **Clarify** if orders from YESPO tracking are needed, given they are already available from CRM.
